# Agent Note: One frame form factor for the whole client

Status: implemented

[English](2026-09-12-frame-form-factor-breakpoints.md) | 中文

## 问题

客户端此前只有一条宽度轴：[列求解器](../../../../packages/client/ui-layout/src/client/columns.ts)的让步链，它决定三列框架各自分到多少空间。但没有任何东西命名手机迫使我们回答的那个更粗的问题——*这个界面还算桌面吗？* 每个注意到问题的功能都私下作答，或者干脆不答；而那些不答的界面在 390px 上一起崩掉：输入栏的两组 chip 相互重叠，统计行在词中间被截断，800px 的设置面板被裁到只剩约 100px 内容列，导致贡献行中文逐字换行，八列的定时任务表格撑出横向滚动条并藏起行内动作，侧栏还占着框架付不起的轨道。

私有媒体查询本身也是错的工具。`@media` 量的是视口，因此被挤窄的列里的组件读到的是它并不拥有的宽度；两个各自猜测断点的功能则会逐渐失配。只有框架知道自己的列最终有多宽。

## 决策

`viewportForm(width)` 把框架宽度归类为三种形态，[AppFrame](../../../../packages/client/ui-layout/src/client/AppFrame.tsx) 把结果作为 `data-viewport` 发布在框架根节点上：

| 形态 | 框架宽度 | 含义 |
|---|---|---|
| `phone` | `< VIEWPORT_PHONE_MAX`（600） | 单列设备。侧栏无法在中间列旁边占一条轨道。 |
| `compact` | `< SIDEBAR_AUTO_COLLAPSE`（1024） | 侧栏自动收成导轨，但仍占一条轨道。 |
| `regular` | 其余 | 完整的三列桌面框架。 |

这就是客户端唯一的断点标尺。功能 CSS 选择这个已发布的属性（`:global([data-viewport='phone'])`），而不是各自声明媒体查询，因此组件无法发明第四种宽度档，而所有界面都与拥有它们的框架在同一瞬间改变形状。这个归类与列求解本身一样是纯函数且无滞回的：两个方向跨越边界完全对称。

相邻的两种工具各守其职。约束组件*自身盒子*的规则——无论什么设备，列一窄就必须换行的输入栏——仍然用容器查询，因为改变的是盒子而不是设备。渲染在框架*之外*的界面仍然用媒体查询：认证文档在任何插件加载之前挂载，此时并不存在能发布属性的框架。

在 `phone` 形态下，侧栏不再争抢宽度。展开的侧栏把自己的网格轨道留在导轨宽度上，改为覆盖中间列，因此中间列几何从不变化、框架保持单列；框架发布 `data-sidebar-drawer` 和求解出的覆盖宽度供绘制它的样式表使用。抽屉后面的中间列变为 inert，一个遮罩按钮提供「点击外部关闭」的出口。遮罩只覆盖抽屉留出的那一条区域：抽屉本身不透明，其下没有什么需要压暗，而铺满整个框架的遮罩会把自己的命中区埋在抽屉底下——手势会落在它本想关闭的面板上。

## 每个界面在 `phone` 形态下的义务

框架负责发布，功能自己决定如何应对。当前的答案：

- **输入栏行**（[ui-conversation](../../../../packages/client/ui-conversation/src/client/skeleton/InputBar.module.css)）——尾部一组在碰撞之前先让出宽度，到最窄档时整行折成两行。用的是容器查询而非框架属性：该行响应的是它所在的列。
- **统计行**——换行而不再截断，并采用手机档更窄的输入栏侧留白。
- **设置面板**（[ui-settings-general](../../../../packages/client/ui-settings-general/src/client/SettingsRoot.module.css)）——变成整屏铺满的 sheet，导航导轨变成横向标签条，关闭控件锚在 sheet 角上。贡献行（外观、字号、语言、权限）占满内容列。
- **定时任务表格**（[ui-scheduler](../../../../packages/client/ui-scheduler/src/client/ScheduleCenterView.module.css)）——每一行变成一张标签/值配对的卡片。表头文字通过 `data-label` 移进各单元格，因此 DOM 仍是一张表，桌面网格不受影响。

## 备选方案

**让每个功能各自声明媒体查询。** 那些还能用的界面本来就是这么做的，也正因如此它们彼此不一致。两个功能分别猜 480px 和 600px，就会造出一条框架已是手机、面板仍以为自己是桌面的区间。它量的东西也不对：被挤窄的列里的组件，空间比视口报告的更少。

**发布 `useViewportForm()` 钩子并在 JSX 里分支。** 按形态渲染不同组件树，会让 100% 覆盖门禁下的客户端包多出一倍需要覆盖的渲染路径，还会把订阅塞进业务组件——分层规则要求实时事实走四份 props share，而不是新的钩子。DOM 保持一种形状，由 CSS 决定怎么画。

**全部改用容器查询、什么都不发布。** 容器查询无法表达*设备*事实。展开的侧栏能否占一条轨道是框架的性质，不是任何单个组件盒子的性质，而侧栏自己的容器恰恰就是那个正在被改变尺寸的东西。容器查询在下一层仍然是正确的工具，这也是两种工具都保留的原因。

**做一套独立的移动端外壳或路由。** 那意味着多一套需要保持对齐的界面，而这个产品的桌面布局本身已是一条解好的让步链。这里每一个手机端缺陷都是既有样式表里少了一条约束，而不是少了一块屏幕。

**在 `phone` 形态下彻底隐藏侧栏。** 导轨承载新建会话、定时任务和设置入口，而框架没有顶栏可以安置它们。保留 56px 导轨要付宽度代价，但保住了每个入口的可达性；发明一套移动端框架来取代它，是比本决策更大的决定。

## 后果

断点如今只在一个地方移动，而形态是可观测的：测试可以断言 `data-viewport`，而不必从几何反推宽度。多数界面只靠 CSS 适配，因此受门禁的客户端包没有增加分支、也没有增加覆盖债——定时任务表格的手机形态就是一张样式表加若干 `data-label` 属性。

代价是功能必须知道这个属性存在才会用它；没有任何机制强制新界面声明手机形态，忘记声明的界面只会渲染它的桌面形状。导轨仍然吃掉 390px 视口中的 56px，这是保住入口可达性的既定代价。

## 测试

`viewportForm` 与抽屉发布的事实在 [ui-layout](../../../../packages/client/ui-layout/tests/app-frame.client.spec.tsx) 有单元覆盖。承载各手机形态的 CSS 契约在 [ui-conversation](../../../../packages/client/ui-conversation/tests/content-width-styles.client.spec.ts) 以解析后的声明断言，而 [apps/web/tests/phone-form.e2e.ts](../../../../apps/web/tests/phone-form.e2e.ts) 用真实的 390x844 Chromium 跑过装配后的产物：已发布的形态、没有横向溢出、输入栏两组保持不相交、统计行未被截断、抽屉及其遮罩几何与关闭、两个对齐的侧栏 footer 触发器、带横向导航的设置 sheet，以及渲染成带标签卡片的定时任务行。
