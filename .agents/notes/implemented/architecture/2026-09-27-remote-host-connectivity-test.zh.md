# Agent Note: 以连通性检测取代远程主机的主机密钥录入

Status: implemented

[English](2026-09-27-remote-host-connectivity-test.md) | 中文

## Problem

添加一台由 SSH 管理的远程主机时，操作者必须先键入规范的 OpenSSH `SHA256:<43 字符 base64>` 指纹，主机才能保存。协调层本来就提供一个不认证的探测，所以这个字段在操作上可以填出来，但它所代表的信任步骤不行：界面要求操作者对该观测到的密钥取得独立核验，而对大多数主机而言并不存在第二条渠道。现实结果就是操作者把探测自己给出的建议值抄回字段，于是被记录的固定指纹恰恰就是它本应佐证的那个未经信任的观测值。

同一张表单还要求操作者在连接前声明远程 `platform` 与 `architecture`。这两个值用于选择本地产物目录，而该目录的清单要按自身的 `node.platform`/`node.arch` 校验，因此它们必须在部署前就已知——但它们是目标主机的属性，而目标主机自己就能报告，且协调层在连接后本就通过运行时状态响应重新核对这些值。

## Decision

主机只有在连通性检测通过之后才会被保存。该检测是一次真实的带身份验证连接，它记录的指纹是这次连接的副产物，而不是操作者的输入。

`RemoteHostSshProvider.probe` 改为 `verify(config, authentication, command, signal?)`。它接受本次尝试的主机密钥，而不与固定指纹比对；它先以传入凭据完成身份验证，仅在身份验证完成之后才运行 `command`，并返回 `{ fingerprint, output }`。观测到的指纹之所以可信，正是因为身份验证是在同一把密钥之下、于其后成功完成的；因此由传输层这一辅助方法返回该证据，而不是交给无法自行证明同样顺序的调用方去推断。

`RemoteHostsProvider.verify({ host, port?, username, secrets })` 负责赋予该检测确切的语义。它通过 SSH 提供方运行一条固定的探测命令，并把回答映射为可部署目标，返回 `{ fingerprint, platform, architecture }`。由于此时连目标的 shell 都还未确定，探测先询问 POSIX 形式（`uname -s`、`uname -m`），若目标是 Windows 默认 shell，则改用编码 PowerShell 重试。若回答未给出受支持的平台或架构，检测以 `UNSUPPORTED_REMOTE_PLATFORM` 失败。

`upsert` 仍然要求 `fingerprint`、`platform` 与 `architecture`，因此「保存前必须检测」是由既有 schema 强制执行的，而不是靠新增的服务端状态。视图保存已完成的检测证据，并以该证据作为保存控件的门槛。平台与架构默认「连接时决定」：编辑器把它们收在默认折叠的可选设置区里，保存时若操作者未显式固定，则以检测证据解析。任何对被检测地址、端口、用户或凭据的修改都会使其失效。

连接时的产物检验失败点名原因，而不是一律压平为 `CONNECT_FAILED`：所选产物目录不存在上报 `ARTIFACT_NOT_FOUND`，存在但检验不过上报 `INVALID_ARTIFACT`，都走载波的封闭 reason 通道；Host 只记录被吞原因的错误名与错误码——绝不记录消息——使操作者文案停留在可行动的 reason 上。

## Alternatives considered

- 保留手工字段并加一个首次使用接受按钮：否决，因为两种信任方式并存会让严格的那一种显得权威，而操作者实际会用的是宽松的那一种；而且表单仍会要求操作者键入一个系统已观测到的值。
- 保留 `probe` 作为不认证的观测，并在其旁新增 `verify`：否决，因为一旦手工字段消失，就没有任何消费方会使用该观测值，这违反仓库关于「不得有无现行归属者的抽象」的规则。拒绝式探测的行为已不再有调用方。
- 把「已检测」作为服务端协调层状态来强制：否决，因为其有效性取决于协调层根本看不到的表单字段（未提交草稿的目标与凭据），于是这条规则将需要服务端会话状态、过期机制，以及与「编辑前须断开」守卫的交互，而它约束的只是已经持有 `harniverse.administer` 的调用方。真正重要的硬性强制没有改变，并且仍在它应在的位置：`hostVerifier` 在每次连接时比对已保存的固定指纹。
- 从远程运行时的 `status` 响应探测平台：否决，因为产物必须在远程运行时部署之前就选定，所以探测不能依赖它；`status` 保留其部署后不一致检查的角色。
- 仅解析 `uname`：否决，因为 Windows 默认 shell 不提供 POSIX 的 `uname`，而探测无法预先知道将由哪个 shell 作答。
- 把探测到的平台视为权威：否决，因为探测覆盖的是产物矩阵，而不是所有合法目标；操作者保留覆盖能力，部署时检查仍会拒绝错误的选择。

## Consequences

被记录的固定指纹，其信任根变为「在一次成功的身份验证之下完成首次接触接受」：同一把密钥被用于一次真实登录，此后任何变化都会在与已存值的比对中触发 `HOST_KEY_MISMATCH`。这在原理上弱于一个经带外核验的指纹，但在实践中强于一张要求核验、最终却收到探测自身回答的表单。主机密钥变化会表现为连通性检测失败，而没有可退回的已存接受记录。

`verify` 需要为一台可能永远不会保存的主机提供凭据，因此它接受一次性秘密，且绝不持久化；已保存的凭据由全新的检测重新验证，而不是直接采信登记表。提供方删除了 `authHandler: []` 这条拒绝路径，因此 `RemoteHostSshProvider` 不再能在不认证的情况下观测密钥。

探测到的平台是默认值，不是保证。`ENDPOINT_IDENTITY_MISMATCH` 仍是最后一道检查，而 `uname` 不可靠的目标需要显式覆盖。

验证位于 SSH 提供方套件（带身份验证的首次接触检测、拒绝时不发送探测命令）、`detect.spec.ts`（POSIX 与 Windows 回答、不受支持的回答、探测顺序）、协调层套件（检测证据、错误净化），以及浏览器视图套件（保存以检测通过为门槛、每个被检测字段的失效、检测值的连接时决定解析、重新检测失败后丢弃陈旧证据）。真实远程验证仍需一台已配置的远程主机。
