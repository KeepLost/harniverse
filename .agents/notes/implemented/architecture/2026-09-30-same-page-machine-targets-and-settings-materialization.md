# Agent Note: Same-page machine targets and host-only settings materialization

Status: implemented

English | [中文](2026-09-30-same-page-machine-targets-and-settings-materialization.zh.md)

## Problem

Opening a remote workspace required a second browser page keyed by `dshRemoteHost=<RemoteHostId>`. Working across machines meant duplicated tabs, each with its own runtime persistence scope, and the remote page interpreted synchronized model settings through its own process environment: a route with no pinned credential silently authenticated with whatever unrelated secret that environment held. Inside one document there was no mechanism to retire a machine's sessions, stores, scopes, and in-flight operations without a reload, so the two-page split was also the only isolation boundary the client had.

## Decision

Machine targets are first-class and switch in the same document. `MachineTarget` — `{ kind: 'host' }` or `{ kind: 'remote', id }` — is the connection layer's routing vocabulary, published through the observable `ctx.connection.target`. `switchTarget(target)` stops the current stream loop, retires the current `TargetGeneration` (whose AbortController cancels the previous machine's unary calls, uploads, and event streams), runs the stream consumer's `onTargetChange` teardown, and starts new streams only after that teardown settles; it resolves without waiting for network readiness, so returning to the host works while a remote is unreachable, and a repeated target shares the existing transition. `captureApi()` binds machine-owned objects to the current generation so their late calls reject; the stable `api` face routes host-management namespaces (`remoteHosts`, `settings`, `credentials`, and authentication) to the page authority and carries everything else through the `dshRemoteHost` carrier parameter.

The runtime replaces its internal Session and Workspace managers per machine while keeping the public services, list sources, and current-provide source: session scopes carry an incarnation tag so addressing or resolving a retired machine's scope fails closed, `SessionListState.targetGeneration` distinguishes machine incarnations even when session ids collide, and session-scoped stores plus selection persistence use machine-keyed namespaces while root UI preferences stay local. `ui-workspace` re-registers its entries per machine through one Cordis-effect generator (clearing search, dialogs, previews, and file caches) and declares `sidebar.workspaces.machine`, where `ui-remote-hosts` mounts the machine indicator — the active machine's name with an unconditional return-to-host action — beside immediate connect feedback and the deploying rows' bounded progress phases (`checking-artifact`, `uploading` with per-file counts, `verifying`, `authorizing`, `starting`, `forwarding`, `synchronizing`).

Settings cross the process boundary as host-only materialized snapshots. `SettingsRegisterOptions.materialize` lets a namespace owner resolve host facts into a detached, schema-validated copy served by `SettingsProvider.materialize(ns)`; the live value, `describe`, and settings events never observe it. `llm-pi-ai` pins ambient credentials this way: for a profile naming no `apiKeyEnv`, the provider's own api-key resolver is asked which of its environment names the credentials service or launch environment answers, and the snapshot carries the winning name plus its `authMode` (`bearer` when the provider's resolved auth carries an `authorization` header, else `api-key`); a route nothing resolves pins `authMode: 'none'`, which disables ambient rediscovery so the synchronized remote cannot authenticate with an unrelated environment key. `llm-deepseek` materializes its resolved endpoint facts (protocol, credential reference, base URL, resolved model list). The SSH coordinator's synchronization consumes materialized snapshots and resolves schema-selected credential references through the credential service; the host process environment is never copied.

## Alternatives considered

- One browser page per machine: rejected because cross-machine work duplicated tabs and persistence scopes, and the management page could not present remote state beside local sessions without a second runtime instance.
- Replacing the global Connection instance in place without generations: rejected because in-flight operations would settle under the wrong machine's authority; `TargetGeneration` retirement plus `captureApi()` make cancellation and late-arrival rejection explicit at the carrier boundary.
- Rebooting the whole client runtime on each switch: rejected because the slot registry, locale, and layout services are page-scoped; per-machine manager replacement retires exactly the machine-owned state while those keep their identity.
- Copying the host process environment or resolved secret values into synchronized settings: rejected because it widens the remote's secret surface and drifts from live settings; materialization carries references and owner-resolved facts only, and `authMode: 'none'` fails closed where nothing resolves.
- Teaching every consumer to filter by machine id: rejected because each filter is one missed check away from cross-machine leakage; generation-bound API captures and incarnation-tagged scopes enforce the boundary once, at the runtime.

## Consequences

One document hosts any connected machine with full teardown isolation: late forks, searches, and file reads from a retired machine reject instead of selecting or caching across the boundary, and returning to the host is immediate. The cost is explicit lifetime machinery in the runtime — `dispose`/`assertCurrent` state in the Session, Workspace, and manager clusters — and machine-keyed persistence keys that a single-machine deployment never observes (`targetGeneration` stays absent there). Remotes keep their synchronized snapshot until the next connect; there is still no live settings subscription, and provider-native credential systems beyond a referenceable key (OAuth flows, AWS-style signing chains) do not materialize, so their routes run remotely unauthenticated — the boundary the `llm-pi-ai` and coordinator READMEs document. The `dshRemoteHost` URL parameter remains the carrier routing key; only the document-scoped entry point changed.

Focused tests cover target generations and carrier retirement (`target-streams`), machine replacement in the runtime and both UI packages (`machine-target`, workspace re-registration, provider-roster reset), coordinator synchronization from materialized snapshots with credential-service resolution (`sync-providers`, `sync`), and the materialization hooks (`llm-pi-ai` ambient pinning including bearer and unresolvable-route cases, `llm-deepseek` endpoint resolution, `settings` detach/validate semantics). Full real-SSH deployment and cross-platform verification remain on the configured Linux test host.
