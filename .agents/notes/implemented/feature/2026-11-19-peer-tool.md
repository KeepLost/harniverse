# Agent Note: The model-facing peer tool

Status: implemented

English | [中文](2026-11-19-peer-tool.zh.md)

## Problem

Pairing (PR #324) and delegation Remotes (PR #325) made paired instances reachable only through the `dsh peer` CLI: the accepting side runs real sessions, but the initiating side's model had no path to them. The subsystem's stated purpose — one instance's *model* delegating to another home — needed a model-facing surface over the existing pairing channel without widening the protocol.

## Decision

Ship one tool package, `dsh-tool-peer`, as a pure Consumer of `dsh-peer-client`: the tool owns the model-facing schema, target resolution, budgeting, and rendering, while proofs, Grant transport, and direct/SSH dialing stay in the client library. Concretely:

- One tool (`peer`, name configurable) with `target` (display name or exact instance id — an id wins over an ambiguous name), `prompt` (bounded at 32768 client-side to mirror the host's own check), optional `session` for continuation, and optional `timeoutMs`. Budgets clamp into 1000–900000 ms with the per-call transport timeout capped at 120000 ms, mirroring the CLI's `boundCallTimeout`/`settleBudget` pair.
- Target reachability reuses the pairing boundary: no allowlist Config. The owner approved a target by pairing it, and the accepting instance's `PeerSurface` fields still gate each Remote family there; ToolRestriction governs the tool's existence per session as for every first-party tool.
- A turn still running past the budget returns `state: 'running'` with continuation guidance naming the session id instead of blocking the model's turn; a settled non-`completed` end reason and every closed peer reason map to tool errors naming the reason. Both choices keep the model-facing contract honest about what happened on the peer.
- The CLI's transport dialing moved into `dsh-peer-client` as `withPeerOrigin`/`withPeerTransport` so the tool and `dsh peer` share one implementation; the SSH provider resolves through `ctx.get('remoteHostSsh')`, keeping the service optional for compositions without it.

## Alternatives considered

- **A dedicated peer allowlist `Config`** — rejected: pairing is already the owner-approved boundary, the accepting instance's `PeerSurface` gates every Remote family there, and ToolRestriction governs per-session tool existence; a second list would duplicate that boundary with no new enforcement point.
- **A second `peer_sessions` listing tool** — deferred: enumeration is low-frequency operator work the CLI already owns; the model reaches its own sessions through continuation, and a listing tool can ship when a consumer asks for it.
- **Long-blocking settlement to completion** — rejected: a tool call holding the parent turn for up to fifteen minutes starves the loop; the bounded budget with continuation guidance keeps the turn responsive and becomes the outbox's submission path.

## Consequences

- Asynchronous receipt and settlement push: the tool blocks within its budget and the model re-asks; the initiator outbox milestone owns queued delivery and result push-back.
- Abort propagation: an aborted parent step does not cancel an in-flight peer call; the per-call transport timeout bounds the wait, and cancellation arrives with the sessioned live channel.
- A `peer_sessions` listing tool: enumeration stays on the CLI; the model reaches its own sessions through continuation.

## Consequences

The CLI's transport dialing now lives in `dsh-peer-client` (`withPeerOrigin`/`withPeerTransport`), so every future consumer of the pairing channel shares one dialing implementation and its validation; the runner lost its private copy and with it the `peer-runner:` message prefixes on transport faults. The `peer` tool's model-visible description, parameter text, and rendered strings are pinned by the ACP snapshot fixtures — editing any of them churns those fixtures by design. Budget clamping mirrors the CLI's `boundCallTimeout`/`settleBudget` pair, so the tool and the CLI can never disagree about what a timeout means.
