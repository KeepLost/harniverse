# Agent Note：定时任务管理面

状态：已实现

[English](2026-09-11-schedule-management-surface.md) | 中文

## 问题

宿主调度器的人类界面此前藏在设置对话框里：按工作区会话成员聚合（每会话一次 Remote 读）、不能把任务绑定到任意会话、不展示任务 ID，运行结果也看不到目标会话。Owner 需要定时任务成为一等界面——侧边栏"设置"上方的入口打开覆盖全部已存任务的管理视图，新建/编辑覆盖绑定、时间、上下文与状态，同时模型侧获得一个编辑动词。

## Decision

### 框架槽位，而不是又一个模态框

`dsh-client-ui-layout` 增加根作用域 `center.view` list 槽与 `ctx.layout.setCenterView(id)`/`clearCenterView()`。被指名的条目以绝对层覆盖中心栏，会话保持挂载于其下并进入 `inert`/aria-hidden——返回会话保持组件身份，切换会话即清除视图（选择会话就是天然出口）。注册只是增加*候选*视图，绝不替换会话本位。这是本次唯一的框架级扩展；侧边栏底部席位（`sidebar.footer.action`）已存在，现改为多占用者纵向堆叠。

### 全局 Remote 走宿主权限，模型走会话属主

`listAll`/`runsOf`（observe）与 `updateAny`/`deleteAny`（operate）以 `harniverse.*` 能力鉴权人类，而不是会话属主检查——管理视图必须能看到并编辑所有记录，包括所属会话已不存在的记录。全局面上的 prompt 修订归属到记录 origin（`createdBy`）：授权的是能力，不是某个会话身份。会话作用域 Remote 仍为会话头弹层做属主检查。

### 模型只编辑指令与状态，不动规则和目标

`schedule_update`（预设作用域、属主检查）替换 prompt 与暂停/恢复。规则替换和任意会话绑定保持人类专属：模型把自己提醒改排进其他会话，等于集中了工具面从未审计过的权力；管理视图则在 operate 能力之后操作。`schedule_create` 仍只绑定 `current`/`job`。

### 目标与规则在所有权处可编辑

`ScheduleTarget` 增加 `session` 种类（任意指名会话，投递时校验）；`update` 接受规则补丁并从当前时刻重算下次到期；已完成的一次性任务拒绝重排。绑定与上下文模式创建后不可变——调度器更新契约没有这些字段，诚实的变通是重建而不是静默改绑。

### 占用是共享的观看事实

一个 `createScheduleViewStore` 实例贯穿底部触发器与中心视图：视图在挂载/卸载时写 `open`（框架是权威），触发器把它镜像为 `aria-pressed`。点击不做乐观写入，因此失败或被清除的视图不会留下卡死的按下态。

## Alternatives considered

- **继续扩展设置分区**（按会话聚合 + 更多表单字段）：放弃——聚合要按会话逐次 Remote 读，且看不到所属会话已消失的记录；设置对话框也不是 owner 每天要开的主工作流的正确归宿。
- **会话之上的模态框**（Settings/Models 先例）：放弃——带抽屉的管理表格需要完整中心宽度，在已是模态的设置流上再叠模态会加剧焦点抖动。
- **让模型同样编辑规则和目标**（与 UI 对称）：放弃——集中了未经审计的权力（自我改排进其他会话）；prompt 与暂停/恢复已覆盖模型在人类复查之间的真实需要。
- **为投递更新引入推送通道**：暂缓——视图在挂载与每次变更后刷新；为环境性更新跨 Remote 缝暂不值得。

## Consequences

- 设置分区注册与其组件被删除；设置对话框的 golden 相应刷新。
- 抽屉以整分钟表达延迟；亚分钟规则仍只能通过模型工具创建。
- 投递驱动的状态变化在下一次视图刷新出现，不做推送。
- `center.view` 槽位成为已发布的扩展点：未来的全中心界面（不限于定时任务）在其旁注册候选，而会话本位保持不可替换。
- 包级规格覆盖 store、触发器、视图与抽屉（含规则锁定与无属主分支）；调度器宿主规格覆盖会话目标投递、规则编辑与全局动词；一条 keyless web e2e 用一次性 `after` 规则驱动完整界面（`every` 规则以当前时刻锚定、创建即触发——golden 最初抓到的确定性陷阱）。表格 golden 归一化了每次运行随机的任务 ID 与日期。
