# Agent Note: Peer artifacts — message-borne files over a communication-only channel

Status: implemented

English | [中文](2026-11-21-peer-artifacts.zh.md)

## Problem

Delegated turns carried text only: an initiator could not hand a peer a file to analyze, and a peer's workspace products were trapped on the producing instance. The roadmap's M7 candidates ranked artifact exchange first because every remaining candidate — remote sub-agent descriptors, workflow peer steps, scheduled delegation — assumes files can move. The owner also corrected the original design direction before work started: **the peer line is communication only; each side's configuration (where files live, how long they persist, what caps apply) belongs to that side's own agent.** An earlier draft of D19 proposed a peer-owned artifact directory on the accepting side with pairing-lifetime retention and `removePeer` cleanup — that violated the principle and was dropped.

## Decision

Artifacts ride the message channel; storage policy never leaves its owning side.

- **Wire vocabulary** (`dsh-peer-protocol`): `PeerUploadManifest` (name, optional media type, exact bytes, base64url SHA-256), the `peer/upload` begin exchange whose result advertises the accepting side's own `maxChunkBytes` and `maxFileBytes`, ordered `peer/append` chunks by absolute offset in canonical base64, `PeerUploadRef` entries on `delegate`/`followup` requests (at most four), and `peer/download` reading one bounded workspace file back. Four closed reasons join the vocabulary: `ATTACHMENT_REFUSED`, `ATTACHMENT_TOO_LARGE`, `UPLOAD_NOT_FOUND`, `DIGEST_MISMATCH`. `PeerSurface` gains a fourth boolean `artifacts`; new pairings grant it through `FULL_PEER_SURFACE`, and pre-artifact records read back with `artifacts: false` (store parse accepts three- or four-field surfaces), so existing pairings stay artifact-off until their owner widens them or approves a peer request.
- **Transient staging** (`dsh-peer-host/src/staging.ts`): `.peer-uploads/<peerId>/` under the accepting home holds in-flight chunks — fifteen-minute TTL, swept each minute, cleared outright at host start. A slot seals only when its complete bytes hash to the manifest digest; a mismatch drops the whole slot. Staging is transport state, never durable configuration: the initiator's retry story is the same synchronous one as any refused call.
- **Admission through the owning pipeline** (`dsh-peer-host/src/delegate.ts`): a delivered message's `uploads` are consumed by re-verifying each digest, committing the bytes through this instance's own `attachments.saveFile`, and delivering the turn with the durable references in the user message's `source.files` plus a `fileHandleText` block naming the read-only handle path for the target model's read tool — exactly the path a local user upload takes. Storage, retention, and caps are the deployment's existing attachment configuration; the peer layer owns none of them, and artifacts belong to the sessions that admitted them — `removePeer` clears pairing and governance, never session artifacts.
- **Downloads** (`peer/download`): one bounded (sixteen-MiB) workspace file from the caller's own `peer-work/<instanceId>/` root, absolute and escaping paths rejected, digest verified by the initiator's `downloadPeerFile` before use. The frame cap is a transport constant like the prompt bound, not a storage policy.
- **Byte budgets** (`dsh-peer-host/src/governance.ts`): the same `peer-governance.json` entry gains optional `monthlyBytes` plus a `spentBytes` bucket per UTC period (retention pruning identical to turns). Every append's chunk is authorized before any byte lands and recorded after acceptance; every delivered download byte records on success. The rejection is the existing `BUDGET_EXCEEDED` naming the period and byte limit — without byte metering the artifact lane would be a budget bypass.
- **Initiator surfaces**: `runPeerDelegate`/`runPeerFollowup` accept `files` (staging loops honor the advertised chunk cap), `downloadPeerFile` wraps the reverse lane; the `peer` model tool gains `attachFiles` (local paths) and `fetchFiles` (workspace-relative paths landing under the initiating home's `peer-downloads/<target>/`, listed in the rendered reply); the CLI gains `--attach` on `run`/`send`, the `fetch` command, and `--artifacts` on `surface`; the dashboard's budget form sets both caps (entered in MiB, metered in bytes) beside the artifacts grant toggle.

## Consequences

- `PeerSurface` gains the fourth boolean `artifacts`; the store parser accepts both three-field (pre-artifact, read back with `artifacts: false`) and four-field surfaces, so `peers.json` stays version 1 and existing pairings remain artifact-off until widened. `peer-governance.json` gains the additive optional `monthlyBytes` and `spentBytes` buckets with identical retention pruning.
- The typert contract for the `peer` namespace now covers nineteen methods; the artifact verbs (`upload`, `append`, `download`) sit behind `harniverse.peer` gated on the surface's `artifacts` field, and the byte-budget rejection reuses `BUDGET_EXCEEDED` so clients classify it with the existing closed vocabulary.
- Staging is deliberately restart-hostile: a host restart invalidates every in-flight upload, and the TTL bounds the worst-case orphan. Both sides treat that as the synchronous-contract norm — a refused or invalidated transfer is an immediate, classified failure, never queued work.
- Byte budgets are per accepting instance and per direction combined into one bucket: a file delivered and fetched back meters twice, which is the honest cost of the channel carrying it. An initiator multi-homing across targets consumes each target's budget independently, matching the fabric's per-home pairing model.

## Alternatives considered

- **Peer-owned artifact directory with pairing-lifetime retention (the dropped D19 draft)** — rejected: it put the peer protocol in charge of the other side's data management. Files now land through the deployment's own attachment pipeline and live with their sessions; retention follows the session's data policy, which is what "each side's agent owns its configuration" requires.
- **Inline base64 in the message body** — rejected: it would bloat the durable transcript, the settlement ledger, and the audit views with megabytes of encoded text, skip digest verification, and pin the transfer size to a single JSON frame. Chunked staging keeps memory bounded and makes integrity structural.
- **Directional enum surface (`'none' | 'send' | 'receive' | 'both'`)** — rejected: D13's narrowing semantics are field-wise booleans; a lateral change (`send → receive`) is neither narrowing nor widening and would force either lateral parking or new semantics, a rework of the just-shipped approval flow for a distinction both verbs' initiator-driven nature already covers.
- **Independent per-artifact cap on the peer channel** — rejected: each receiving end enforces its own attachment cap and advertises it in the begin result, so the initiator fails fast without transferring; a second peer-defined cap would be the channel owning what the deployment already owns.
- **Scheduled delegation inside this milestone** — deferred to its own small PR: M7 already spans protocol, host, client, tool, CLI, and UI; attaching scheduler wiring would widen the blast radius for a feature with zero protocol overlap.

Per-file statement and branch coverage is 100% across the touched `src/` trees; type-equivalence blocks, the cordis catalog, the config catalog, and the module graph are regenerated with all 1360 translation pairs consistent.
