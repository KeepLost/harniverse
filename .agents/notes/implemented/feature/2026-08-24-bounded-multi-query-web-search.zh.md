# Agent Note: 有界多查询 Web 搜索

Status: implemented

[English](2026-08-24-bounded-multi-query-web-search.md) | 中文

## 问题

`web_search` 只接受一个标量查询，因此模型比较多个主题时必须发出多次工具调用。这会成倍增加保留的工具调用开销，让跨查询来源顺序取决于调用时序，也无法共享一个结果上限。若把批量形状移入 Web Service Definition 或提供方适配器，则会迫使每个后端实现批处理，并让提供方无关 seam 与面向模型的编排事项耦合。

批处理还需要完整的生命周期约定。无界 fan-out 会放大提供方成本；快速失败可能在工具报告失败后仍留下运行中的兄弟请求；直接拼接提供方列表会让较早的查询耗尽全部结果预算；合并后不带查询标签的提供方答案则会丢失来源信息。

## 决策

`@deepseek-ai/dsh-tool-web` 拥有有界多查询编排。面向模型的 `web_search` schema 只有一个必需属性 `queries`，其值为字符串数组，不含标量 `query` 属性。`searchMaxQueries` 默认为 `4`，必须是正整数，且不能超过固定协议最大值 `16`；解析后的值会出现在工具描述和系统提示词指引中。验证要求数组在调用任何提供方前包含 1 至 `searchMaxQueries` 个非空白字符串。

Consumer 先检查提交数组的长度，再按完全相同的查询字符串去重并保留首次出现顺序。虽然全空白项无效，但去重时空白仍有意义。此顺序可防止用重复值绕过配置的准入上限。

提供方边界保持标量。每个不同查询都会变成一次并发的 `ctx.web.search({ query, maxResults }, signal)` 调用，因此 `WebSearchRequest`、提供方注册表以及 DeepSeek、Exa 和 Perplexity 适配器都保留单查询约定。单项数组走直接路径并原样转发调用方信号；批处理属于 Consumer 的私有编排，而不是新的能力 seam 操作。

对于两个或更多不同查询，Consumer 会在调用方信号与批次自有中止控制器所融合的信号下并发启动所有搜索。最先观察到的失败会中止所有兄弟查询的融合信号。Consumer 随后通过 `Promise.allSettled()` 等待每个已启动搜索 settle，最后才返回第一个失败。调用方取消走相同的完全停稳路径。提供方必须遵守取消以便及时停止，但即使兄弟查询不配合取消，工具也要等其 settle 后才声明批次已结算。

成功结果在一个全局 `searchMaxResults` 上限内合并。来源先按提供方 rank、再按查询顺序访问，从而在查询之间形成公平的 round-robin；较短的结果列表耗尽后自然退出。全局按完全相同的 URL 字符串去重，并保留首次遇到的来源对象。如果任一提供方结果已截断，或合并过程在全局上限处丢弃了不同来源，合并结果都会把 `truncated` 设为 true。

每个非空提供方答案都会按提交的查询顺序保留为 `### <query>` 区段。合并答案、合并后的结构化来源和截断标志共同成为规范工具值及持久化 `tool/result` 元数据，用于重现 Web 搜索卡片。普通持久化 `tool/call` 会保存精确的 `queries` 数组，因此模型可见输入与合并输出都能从 Session 事件日志重建。

标量旧式形状 `{ query: "..." }` 会被有意以 `INVALID_ARGS` 拒绝。Harniverse 尚处于预发布阶段，对该工具 schema 不存在持久化或外部兼容承诺；单查询调用方使用 `{ queries: ["..."] }`。交付内容不包含双重 schema、参数重写或隐藏回退。

## 测试

`packages/web/tool-web/tests/tool-web.spec.ts` 钉住仅数组的必需 schema、默认及配置查询上限、协议最大值、调用提供方前完成验证、完全相同查询与 URL 的去重、并发启动、按查询标记答案、较短结果耗尽后继续 round-robin、全局结果上限、兄弟取消、调用方取消，以及返回失败前的完全停稳。`packages/web/tool-web/tests/integration.spec.ts` 通过真实 Web seam 与 Exa 提供方适配器执行单项数组，仅替换网络边界。

`apps/web/tests/web-search-round.e2e.ts` 及其无密钥回放 fixture 通过真实组装 Web 组合与确定性本地提供方端点执行双查询工具调用。它们钉住两个标量提供方请求、持久化 `tool/call` 的 `queries` 数组、合并且封顶的 `tool/result` 文本与元数据、共享 URL 的精确去重，以及已结算的浏览器卡片。额外的 Exa 与 Perplexity 组合证明，同一双查询 Consumer 约定可以在无需外部 API key 的情况下与两个标量适配器组合。

## 考虑过的替代方案

**把 `queries` 加入 `WebSearchRequest`，并在每个提供方内批处理。** 否决，因为批处理是模型工具的编排事项。它会扩宽 Service Definition，在适配器间重复并发与取消策略，并迫使只有标量 API 的提供方各自模拟相同的 fan-out。

**保留标量 `query`，要求模型发出并行工具调用。** 否决，因为每次调用都会拥有独立的结果上限和保留包络，无法跨调用保证来源公平性、精确 URL 去重、答案来源信息与兄弟完全停稳。

**同时接受 `query` 与 `queries`。** 否决，因为预发布仓库没有要求保留两种模型可见形状的兼容承诺。联合形状会消耗 schema token，需要为同时携带两个属性的调用定义优先级，并保留一条无法表达本功能的路径。

**一个兄弟查询失败后立即返回。** 否决，因为提供方工作可能在工具结果成为最终状态后继续运行并发布副作用。先取消再等待全部 settle，可为操作提供唯一可观察的生命周期边界。

**按查询逐个拼接结果。** 否决，因为较早的查询可能在后续查询贡献任何来源之前耗尽全局上限。以 rank 为先的 round-robin 可让每个非空查询获得公平机会，同时保持确定性的查询顺序。

**去重前规范化查询或 URL。** 否决，因为大小写折叠、空白改写、重定向、片段和 URL 规范化可能改变提供方语义或合并不同资源。完全相同的字符串标识是确定性的，也不会凭空制定等价策略。

## 后果

一次工具调用可以搜索多个相关表述，同时只保留一个有界结果和一份持久化展示。默认允许四个并发提供方请求；部署可以降低该值，也只能提高到十六。因此，提供方成本与限流压力会随配置上限增加，但不会因模型给出无界数组而无限增加。

提供方包与 Web Service Definition 保持插件原生且使用标量。Consumer 承担编排复杂度：它为每个不同查询分配一次请求，在失败时等待完全停稳，并可能等待忽略取消的提供方。公平合并可能为了后续查询的高 rank 来源而省略较早查询的低 rank 来源，这是共享一个全局上限的预期代价。

该 schema 变更在发布前有意保持破坏性。已存 fixture 与调用方必须使用 `queries`；拒绝 `{ query }` 可保持唯一且无歧义的约定，避免把推测性的兼容代码带入首个发布格式。
