# Agent Note: 接管持有者已退出的写入锁

Status: implemented

[English](2026-10-02-exited-holder-lock-takeover.md) | 中文

## 问题

[dsh-atomic-write](../../../../packages/util/atomic-write/README.md) 的 `withFileLock` 以独占创建生成 `<file>.lock`，并在 `finally` 中移除它。进程若在没有执行该 `finally` 的情况下结束——崩溃、SIGKILL、无信号处理的 Ctrl-C、或释放与恢复写入的竞速——就会留下锁文件，该文件的后续写入方全部超时，直到有人手工删除。最初的决策接受这一点，因为锁龄无法区分已崩溃与被暂停的持有者。

## 决策

- 锁记录 `{ pid, hostname, nonce }`。随机数保证每条记录唯一，后来的锁绝不重复已退出持有者的记录。
- 竞争者读到锁后解析其记录。当记录指向本机且对该 PID 的信号探测以 `ESRCH` 失败时，持有者被证实消失，锁被接管。`EPERM` 表示进程存在于另一用户之下，锁保持等待。
- 读到同一记录的竞争者通过以 `wx` 创建的声明文件 `<file>.lock.takeover-<记录 SHA-256 前 16 位十六进制>` 串行化。认领者重读锁，仅在记录未变时移除锁，随后删除声明并立即重试获取。记录只能经另一次接管改变，而接管需要同一声明，因此认领者绝不会删掉另一竞争者在原持有者之后取得的锁。
- 空记录、无法解析、缺少主机名、指向他机、或 PID 为零或负数的记录一律等待。这些都不能证明持有者已停止。
- 更早版本只记录 PID 的记录同样视为本机写入，因此改动之前遗留的锁也会被接管。

Harniverse 的 `withFileLock` 保持无参数签名与 2 秒协议期限；接管发生在首次竞争迭代上，因此接管成功不付出退避代价。

## 备选方案

**按固定锁龄移除。** 锁龄无法区分已崩溃的持有者与正在执行长时合法操作的持有者，插件式工作负载合法地持锁数分钟。

**内核释放锁（`flock`、`LockFileEx`）。** 持有者死亡时内核直接释放锁，这消除了问题而非检测它。代价是每个 `withFileLock` 调用方都依赖一个全平台原生绑定；若 PID 复用或异机记录日后成为问题，这仍是更强的修复。

## 测试

接管测试使用一个确实已退出的真实子进程。对同一记录的并发接管逐个放入且无残留。等待测试覆盖存活持有者（两种记录格式）、异机、不可读锁、已被声明的记录、EPERM 持有者与畸形记录；声明失败测试覆盖 Windows 删除未决、非竞争失败与无法移除的声明。

## 后果

同机上写入方不再因死亡持有者的锁而死锁。被存活进程复用的 PID 保持其锁直到操作者移除，他机写入的锁（共享文件系统）绝不被接管。于 2026-10-02 wave-4 吸收期间移植自官方 DSH `7e7ba139fd`（Turtle）。
