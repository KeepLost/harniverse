# Agent Note: Composer 事务安全与缓存命中率精度

Status: implemented

[English](2026-08-24-composer-transaction-and-cache-precision.md) | 中文

## 问题

Web 会话 composer 会乐观清除普通发送，并让默认 sink 在输入状态机的提交事务之外继续执行。因此，当引用序列化、图片编码或 Host 接纳仍未结算时，再次按 Enter 可能重复提交同一草稿。失败恢复则必须在所有权已经转移后重建文本与图片，这可能覆盖后来输入的文本、复用已由另一发送取得的图片，或在会话 scope 释放后继续发布状态。

纯图片提交采用另一条没有进行中 owner 的 fire-and-forget 路径。重复激活会重复发送，并发文本发送则可能捕获同一组草稿图片 id。只中止可见状态机状态并不足够，因为序列化器、sink 与上传 promise 在输入壳释放后仍可能存活。

同一统计行还存在精度缺陷。`Math.round(cacheReadTokens / billedInputTokens * 100)` 会把足够接近全命中但并不完整的缓存命中率显示为 `100%`。面向用户的全命中标签必须精确表示未缓存输入与缓存写入都为零；即使 token 计数接近 `Number.MAX_SAFE_INTEGER`，也不能把计数乘以不断扩大的十进制比例而超出安全整数运算范围。

## 决策

每次带文本的 Queue、Steer 与 slash 未命中发送都由一个 `SubmitAttempt` 负责，范围从 Enter 开始，覆盖可能存在的 adjudication（判定）、引用序列化、浏览器图片编码，直至 Host 提示词接纳。输入状态机保持 `submitting`，直到该事务的 `SubmitOutcome` 结算，因此重复 Enter 会被忽略，而不会创建第二个生命周期 owner。Queue 与 Steer 保留原始手势捕获的模式；事务所有权不会提升、重排或改变投递策略。

带文本发送成功时只消费已提交的草稿快照与捕获的图片 id。接纳未决期间追加的纯文本后缀会保留在 composer 中；对于无法与已提交快照安全分离的交错编辑，系统不会猜测如何恢复。错误与 rejection 会保留实时草稿，并释放同一个提交席位以供重试。

纯图片发送拥有独立且唯一的 `ImageSendAttempt`。未决期间，它会预留捕获的图片 id、抑制重复的纯图片激活，并使并发文本发送无法使用这些 id。失败会释放预留但不移除图片。成功只移除捕获的 id，而且仅当输入状态机仍处于 plain 状态时才消费捕获的文本快照，因此后续命令或 adjudication 事务会保住自己的草稿所有权。

输入壳会保留每个 adjudication、序列化与 sink 的完成状态。release 会中止活跃的状态机事务与纯图片控制器；事务信号会传入引用序列化器和 sink，sink 再将其转发给图片编码与 Host 接纳。迟到的结算不会发布任何状态。dispose（资源释放）会加入同一个已记忆的 drain，并且仅在所有保留的完成状态结算后才解决；一个序列化器失败时会中止其余兄弟序列化器，并在解锁事务前等待整个 fan-out 结算。

仅当 `uncachedInputTokens + cacheWriteTokens` 精确为零时，缓存命中率格式化才返回 `100`。普通比例继续使用整数显示。当整数舍入会把未完全命中的比例显示为 100 时，格式化器会找出舍入后仍低于 100 所需的最少小数位。它使用商余分解和较小的有界因子比较安全整数 token 计数，而不是把完整分母乘以无界的 10 次幂，因此在受支持的 `number` 范围内仍能精确区分。

## 考虑过的替代方案

**乐观清除，并在失败时恢复。** 不予采纳，因为恢复发生在后续编辑和附件变化之后。如果不让发送快照首先成为事务 owner，就无法区分已提交前缀与新的用户意图。

**让 sink 保持 fire-and-forget，并使用一个重复布尔值。** 不予采纳，因为 sentinel 并不拥有取消、引用 fan-out、上传、Host 接纳或拆卸结算。一个被保留的事务完成状态表示整个操作，并提供所需的完全停稳边界。

**对文本与纯图片发送使用同一个全局锁。** 不予采纳，因为未决的纯图片发送无需阻止新输入的文本、命令或 adjudication。只预留捕获的图片 id，就能在保留独立有效输入的同时避免重复的附件所有权。

**release 时中止但不等待完成。** 不予采纳，因为取消是协作式的。序列化、浏览器文件读取或 Host 接纳可能在观察到信号后才结算；只要这些 owned promise 仍然存活，dispose 就不能报告完全停稳。

**缓存百分比保持整数，并把未完全命中钳制为 `99%`。** 不予采纳，因为这种做法虽避免了错误的 `100%` 标签，却会丢弃有意义的精度，使 `99.95%` 与 `99%` 无法区分。

**使用浮点比例、任意精度依赖或无界十进制缩放。** 浮点舍入正是该缺陷的来源，为显示格式化新增数值依赖并不相称，而无界缩放可能离开安全整数范围。商余比较用有界 `number` 运算即可提供所需的精确顺序。

## 验证

Composer 事务测试固定普通 Queue、Steer、slash 未命中与纯图片路径的重复抑制；错误结果、rejection 与同步 throw 后的重试；后缀保留；捕获图片的提交；跨并发文本发送的图片预留；以及对并发命令和 adjudication 草稿的保护。生命周期用例断言中止信号传播、不存在迟到发布、序列化器兄弟取消，以及 dispose 会等待 adjudication、序列化与 sink 结算。

统计格式化测试固定普通整数舍入、多个接近全命中的小数边界、精确全命中，以及 `Number.MAX_SAFE_INTEGER` 附近只缺一个 token 的情况。组件覆盖确认最少区分精度会抵达渲染出的缓存命中率标签。

## 后果

每次已接纳的 composer 发送都由同一个 owner 从手势负责到 Host 结果，因此重复抑制、重试、取消与拆卸都指向同一操作。新文本与图片按照明确的快照和预留规则保留，同时 Queue 与 Steer 行为保持不变。忽略中止的协作式工作可能延迟 scope dispose，因为如实达到完全停稳优先于遗弃 owned promise。

在极端安全整数场景下，接近全命中的缓存命中率可能使用较长的小数标签，而常见数值仍保持紧凑的整数或短小数显示。显示永远不会把 `100%` 当作近似值：该标签只用于数学意义上的完全缓存命中。
