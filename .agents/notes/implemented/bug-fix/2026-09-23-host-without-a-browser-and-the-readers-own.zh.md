# Agent Note: 无法启动的浏览器面板，与无处可去的链接

Status: implemented

[English](2026-09-23-host-without-a-browser-and-the-readers-own.md) | 中文

## Problem

有一处部署在其运行的机器上报告 `No browser executable was found in this execution environment`，而面板除了这句话之外拿不出任何东西。这一个症状背后是两个彼此独立的缺口。

诊断没有给出任何事实。控制器会探测 `executablePath`，否则按顺序探测`browserCandidates`，但那条消息既没说它找了什么，也没说路径是可配置的，于是唯一能修好它的人——那台机器的运维——只被告知「尝试失败了」。候选列表本身也不对称：`microsoft-edge`以其 Linux 名称被探测，而 Edge 在 macOS 与 Windows 上的安装路径却缺席，因此一台只装了 Edge 的Windows 或 macOS 宿主机，会在一条本该覆盖它的探测上失败。

更糟的缺口在链接上。只要外壳组合进了宿主浏览器面板，`ui-conversation` 就把 assistant正文中的普通左键点击路由给它，而面板是否可用从来不是这个决定的一部分。于是在一台没有浏览器程序的宿主机上，每个markdown 链接都落进一个什么都加载不出来的面板，读者也无法表达「那就在我这边打开」——而那个目的地从始至终都能从他们自己的机器到达。

## Decision

报告这台机器自己的事实，并让读者选择机器。

`noBrowserReason` 用探测实际查找过的内容组成「不可用」原因——配置的路径，或候选列表——并点明补救办法是`executablePath`。两处报告「没有浏览器」的位置都使用它，因此 `environment` 的`unavailableReason` 与 `create` 的 `browser-unavailable` 失败携带同一段文本。面板把该原因渲染在其本地化提示之下：本地化的句子可以点明补救途径，而只有宿主知道自己试过哪些名称。Edge的 macOS 与 Windows 路径加入候选列表，与早已在列的 Linux 名称对齐。

`MarkdownExternalLinks.open` 现在返回持有方是否接下了该目的地，而 `renderSafeLink`仅在它接下时才抑制锚点。这正是后半部分的全部机制：拒绝接过的持有方会留下一个带着`target="_blank"` 的普通锚点，于是目的地通过浏览器原本的行为、在发起该次点击的同一手势之内，在读者自己的浏览器中打开。另一种做法——由持有方调用`window.open`——会是一个脱离手势的开窗请求，会被弹窗启发式拦截，读者将什么都看不到。

这个选择本身是一项持久化偏好 `ui-conversation.linkDestination`，与 `busyEnter`并列在同一段落、同一通用设置列表中：`panel`（默认，保留宿主机的网络位置，也是面板存在的理由）或`device`。opener 以实时快照的方式读取它，而不是在 apply 时捕获一个值，因此更改无需重新加载即可作用于下一次点击。选择`device` 时，opener 拒绝接过任何目的地，无论是否有面板；选择 `panel` 而没有面板被组合进来时，它同样拒绝接过——这正是旧的`window.open` 分支想要表达的意思。

两个设置行现在共用 `PreferenceSelectRow`：两项偏好的呈现完全一致，因此外壳是一个组件，各行只保留自己的词汇与inject 面。

## Testing

`sandboxDisabled` 那种真值表在这里并不适用，因此证据是行为性的。控制器测试固定了两种原因形态——探测过的候选列表，以及一条并不存在的已配置路径。面板测试断言宿主给出的原因渲染在提示之下，并断言一台没有进一步说明的宿主机仍只显示提示本身。`MarkdownText`新增了「持有方拒绝接过」的用例：锚点保留 `target="_blank"`，且点击未被阻止。对话的 apply测试覆盖了路由决定的每一侧——没有面板、有面板、读者的选择、重新发布同一段落，以及跟随实时值的持久写入。

端到端的证据是一个真实的标签页：markdown 链接场景通过设置对话框切换偏好、点击链接，并等待浏览器上下文在该URL 打开一个页面，同时面板保持缺席。设置对话框的 golden 已为新行刷新。

## Alternatives considered

**让对话侧知道哪些宿主机有浏览器。** opener 本可以查询宿主可用性，仅在面板确实无法服务该链接时才拒绝接过，完全不需要偏好。可用性是一项按Session的宿主事实，面板控制器在视图首次绑定会话时才得知，因此对话侧将不得不通过一个新的跨包信号提前获取它——而一位在**确实**装有浏览器的宿主机上单纯偏好用自己浏览器的读者，仍然无从表达。偏好同时回答了两者，而且回答得确定。

**客户端侧的浏览器路径设置。** 被报告的那条消息要的就是一个浏览器路径，让面板用户直接填写很有诱惑力。但可执行文件位于宿主机上，是一项部署事实：`executablePath`是经校验的插件 `Config`，通过 patch 层触达；让客户端选择宿主执行哪个程序，等于把关于宿主进程执行的决定交给一个浏览器侧的界面。面板改为点明这个键。

**由持有方打开标签页。** 保留 `open(url): void`，并在面板无法服务链接时调用`window.open`，不需要任何契约变更，而且这正是此前在「无面板」情形下的做法。它恰恰在最要紧的时候失效：该调用发生在点击已被取消之后，于是浏览器视其为未经请求的弹窗。拒绝接过既更小也更诚实——持有方说「这不是我的」，平台便照它一向对待链接的方式去做。

## Consequences

对本仓库内的 markdown 持有方而言，`MarkdownExternalLinks.open`是一次破坏性的签名变更；现在每个实现都要返回布尔值，而忘记返回的持有方会失去接管能力，而不是直接报错。类型让这成为编译错误，这正是它该出现的地方。

使用 `device` 的读者再也无法从正文触达宿主机本地的目的地——指向宿主机自身 `localhost`的链接会打向他们机器的 `localhost`，从而失败，或者更糟，命中属于他们自己的某个服务。设置项的描述陈述了这一取舍，而`panel` 仍是默认，正因为宿主机的网络位置就是面板的全部价值。

对话插件现在在同一段落中拥有两个持久字段，因此它的 settings scope 在 `apply`中绑定一次并共享。第三项偏好应沿同一路径，而不是为同一命名空间再绑定第二个 scope。
