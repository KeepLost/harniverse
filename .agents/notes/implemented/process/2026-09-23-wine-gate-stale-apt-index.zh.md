# Agent Note: Wine 门用陈旧索引安装了缓存闭包

Status: implemented

[English](2026-09-23-wine-gate-stale-apt-index.md) | 中文

## Problem

阻塞性的 Wine 门连续四次失败在同一行上：`libgstreamer-plugins-base1.0-0 1.24.2-1ubuntu0.4` 的 404——这个文件已不在任何 Ubuntu 池中，所有镜像都已转向 `0.5`。该作业看上去像一次镜像故障，而且重跑确实清掉过一次，这正是它显得像偶发抖动的原因。

它不是抖动，也不是镜像的问题。该步骤有两条路径：当 `~/wine-debs` 中有闭包时安装缓存的 deb 闭包，否则下载闭包再安装。只有下载路径跑了 `apt-get update`。运行器镜像自带烘焙好的 apt 列表，因此在缓存路径上，apt 是对着一份仍指名已撤回文件的索引去解析该闭包的依赖，而这条路径里没有任何东西能纠正它。缓存每次运行都命中，于是这道门的健康完全取决于运行器来自哪个镜像世代：烘焙列表仍然当前的世代通过，而列表已经过期的世代则会持续失败，直到缓存过期。

## Decision

在解析任何东西之前先刷新索引，两条路径都刷新；并把当前索引无法满足的闭包视为已耗尽而不是一次临时故障——该步骤将其丢弃，使下一次尝试去下载一份新的。

这保留了缓存的用途。它的存在是为了让一道只需要一个 `wine` 可执行文件的门省下 108 MB 下载，而不是为了把某个特定的 Wine 构建钉住；因此替换一份已经装不上的闭包只花掉一次慢速运行，之后快路径即恢复。

## Testing

这只在 CI 中运行。在此前一直失败的同一镜像世代上，这道门从连续四次失败转为 4 分 48 秒通过，走的是丢弃并重新下载的路径，该次运行的 `all checks passed` 门也随之转绿。

## Alternatives considered

**重试下载。** 第一次尝试在下载周围加了有界重试，其假设是某个镜像落后于它自己的索引。它从未执行到第二次尝试，因为失败的是缓存路径，根本没有走到那个循环。而且重试无论如何都帮不上：那个文件是从所有池中消失了，不是发布得晚。

**把镜像源改写为官方 archive。** 第二次尝试在失败时回退到 `archive.ubuntu.com`，把运行器的镜像列表当成了陈旧的一方。镜像列表本身没问题——对它执行 `apt-get update` 得到的就是 `0.5`。这会用一个更慢的下载换掉本该正确的修复。

**把缓存键换成更短命的。** 更早过期的键只会限制陈旧窗口而不是消除它，并且要为此更频繁地付出那 108 MB 下载。

## Consequences

这个作业的每次运行现在都要付一次 `apt-get update`，对一道耗时数分钟的门而言是几秒钟。

缓存闭包只在 archive 仍能满足它的期间存活，因此某个撤回之后的第一次运行会慢。这正是预期的取舍：这道门讲的是 Windows Node 在 Wine 下的真话，而它的环境准备不是一个适合耍花招的地方。
