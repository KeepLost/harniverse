# @deepseek-ai/dsh-shell-registry-settings

English | [中文](README.zh.md)

Root-owned settings namespace for the shell registry: the `shell-registry` section of `$DSH_HOME/settings.yaml` holds the user-registered shell entries and the default sessions fall back to when they select none themselves. Two builtin ids are always addressable without registration — `posix` (the platform's default POSIX shell: zsh on macOS, bash on Linux, Git Bash on Windows) and `pwsh` (PowerShell) — and an explicit default is honored on EVERY platform.

## Fields

| Field | Schema | Default |
| --- | --- | --- |
| `default` | `'platform-default' \| 'posix' \| 'pwsh' \| <entry id>` | `'platform-default'` |
| `entries[].id` | unique lowercase slug, never a reserved id | — |
| `entries[].path` | executable path or PATH name classifying into a served dialect class | — |
| `entries[].label` | optional display label (default: the executable's basename) | — |

Validation is loud at the earliest resolvable point: reserved or malformed ids, duplicates, executables outside the served dialect classes (POSIX bash/zsh/sh/dash/ksh; PowerShell pwsh), and defaults addressing no registered entry all fail the namespace registration or update.

The namespace registers `applies: 'restart'`: app boot (`@deepseek-ai/dsh-app-boot`) reads the stored document once per start — an explicit non-blank `$DSH_SHELL_BACKEND` env value wins, the same escape-hatch shape as `$DSH_PERMISSION_MODE` — and publishes the resolved stack into `$DSH_SHELL_BACKEND` (plus a custom default entry's executable into `$DSH_SHELL_DEFAULT_PATH` for single-stack hosts) before the config tree mounts. The shell rows' `disabled` expressions consume that value symmetrically, so exactly one shell stack mounts per host and a committed settings change applies on the next start. In-process, the plugin exposes the resolved document as the `shellRegistry` service: the shell router probes every entry through it at mount, and the session-shell resolver reads it as the single source of the host default.

Loader entries start concurrently, which is why the composition-time chain stays static instead of a runtime service gate: a service published by an earlier row would race the executor rows' activation. The REAL-composition suite in this package boots the whole chain through the Loader (seeded document → boot bridge → flag pair) and pins both stacks' outcomes.

The web client reaches this namespace through `settings.describe` / `settings.update` (the gateway's `WEB_SETTINGS_NAMESPACES` allowlist names `'shell-registry'`), so the Settings page edits the same document.

Sandbox posture is unchanged by any selection: entries route through the composed stacks' existing confinement, and a selected shell that fails to launch under confinement surfaces as `SANDBOX_UNAVAILABLE` from the executor.

## Model Experience

### Shell registry defaults

#### What the model sees

The runtime-context shell fact names the actual shell of the session's effective entry (for example `zsh` with its POSIX-compatible syntax note), generated by the single resolver in `@deepseek-ai/dsh-shell`; no prompt sections or schema fields are added or removed by the registry itself.

#### Token effect

None beyond the one pinned fact line the session-shell context already contributes.

#### KV Cache effect

None; the registry is read once per start and never enters per-turn assembly.

## Known Limitations and Deferred Work

- Single-stack hosts (dsh-base compositions without the shell router) honor a custom default's executable through `$DSH_SHELL_DEFAULT_PATH` but cannot switch per session; switching requires the router composition.
- Git Bash under the win32 ACL restricted-token sandbox has not been validated on real Windows hardware (wine CI cannot exercise the koffi/ACL path); a confined Git Bash that hits a runner-launch failure under confinement reports `SANDBOX_UNAVAILABLE` per call, and the keep/gate/pair-with-full-access decision rides that result.
