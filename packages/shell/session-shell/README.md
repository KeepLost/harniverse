# @deepseek-ai/dsh-session-shell

English | [中文](README.zh.md)

Session-scoped shell pointer over a routed [`ctx.shell`](../shell/) seam: the `sessionShell` service owns which shell-registry entry a session's next model request runs under. Compose together with [`dsh-shell-router`](../shell-router/) (the substrate that mounts both stacks and probes every registry entry) — `dsh-tool-bash` and `dsh-tool-pwsh` both stay registered, and the pointer retires the inactive stack's tool for that session.

The package root exports `SessionShellService`, the `session-shell/change` event type, the `sessionShell` projection, the `SESSION_SHELL_CONTEXT` section, and the pinned `CONTEXT_TEXT`.

## Behavior

- **Epoch semantics.** `switch(agent, entry)` validates liveness, router availability, and the target registry entry (legacy `bash`/`pwsh` family values fold onto the builtin entries), then appends one durable `session-shell/change` event and folds the `sessionShell` projection (last-wins). The switch is effective at the NEXT model request: the runtime-context snapshot announces the new shell — fact line plus a pinned change notice naming both sides — and the retired stack's tool leaves that request's catalog. In-flight shell calls complete on their frozen promise; background terminals and persistent shells of both stacks keep running; nothing is torn down.
- **Per-agent tool restriction.** At `agent/created` and at each switch, the service applies `tools.restrict({ deny: [otherFamilyTool] })` on the agent's scoped context — the same visibility resolver that feeds presentation, lookup, and dispatch — so the retired tool disappears from schema, lookup, and execution atomically for that agent. Agents whose context carries no scope (structural stubs) skip restriction instead of throwing.
- **Serialized mutations.** Concurrent switches on one agent serialize; the last one wins in order, and a rejected operation leaves the queue drained.
- **Capability read.** `describe()` answers `{ switchable, families }` — routed hosts report the router's availability; single-executor hosts report their boot default with `switchable: false`. Router detection is structural (`availability()` presence), never `instanceof`.
- **Single resolver.** The prompt fact, the tool-catalog restriction, and the execution stamp (`dispatchTarget`, read by `dsh-tool-bash`/`dsh-tool-pwsh` to stamp `shellPath`) all derive from `resolveEffectiveShell` in `@deepseek-ai/dsh-shell`. Each prompt assembly freezes the session's effective shell as the dispatch promise — the exact executable the model was told runs — so a mid-request switch can never make a call execute a shell the request was not told about. Default resolution for a session with no recorded override: the routed default entry (which folds the boot pins and the registry default), else an explicit registry default, else the platform split; an orphaned or unavailable target degrades to the platform builtin inside the resolver with a reported reason, never a silent substitution.

```yaml
- id: shell
  name: '@deepseek-ai/dsh-shell-router'
- id: session-shell
  name: '@deepseek-ai/dsh-session-shell'
```

The HTTP surface is `session.shell` (observe) and `session.switchShell` (operate) on the sessions API; hosts without this service answer `shell-unavailable`.

## Model Experience

### Runtime context section

#### What the model sees

One pinned line naming the session's actual shell (label, plus the declared path for absolute-path entries) and its syntax, generated by the single resolver and contributed into the runtime-context snapshot. After a switch, the next assembly's partial context snapshot carries the new line plus the pinned change notice (`The session shell changed from X to Y; shell commands now run under Y.`); the notice rides exactly one assembly.

#### Token effect

One line per request inside the runtime-context section.

#### KV Cache effect

An entry switch appends a partial context snapshot (the standing mechanism for per-request facts); the system prompt and retained history prefix stay byte-for-byte, so existing KV-cache entries remain reusable.

### Family tool visibility

#### What the model sees

Only the active stack's tool (`bash` or `pwsh`) appears in the request's tool catalog; calling the retired stack's tool in the same breath the switch lands yields `UNKNOWN_TOOL`, which the runtime answers with the standard unknown-tool guidance.

#### Token effect

One tool schema instead of two.

#### KV Cache effect

Tool-catalog changes ride the same request-boundary snapshot; append-only for history.

## Known Limitations and Deferred Work

- **Switching needs the router** — on single-executor hosts `switch` refuses and `describe()` reports `switchable: false`; there is no executor-migration story for hosts that compose exactly one family.
- **Restriction is agent-scoped, not session-scoped** — a session resumed under a composition whose registered tools differ still gets its initial restriction recomputed at `agent/created`, but compositions that register neither family's tool have nothing to retire.
- **The projection folds on dispatch** — the committed map bridges the append-to-dispatch window so back-to-back switches cannot read a stale family; readers of the durable log alone see events in order.
