# Harniverse 版本与分支策略

[English](release-policy.md) | 中文

本参考文档规定产品版本、集成、稳定化与发布选择。没有会话历史而接手发布工作时，从这里开始；[发布族决策](../.agents/notes/implemented/process/2026-08-10-npm-release-sequences.md)负责包边界与发布机制。修改仓库前先阅读根目录的[贡献者说明](../AGENTS.md)。

## 恢复当前状态

检查工作区、当前分支、上游跟踪关系、远端发布分支、附注发布标签与 GitHub releases。读取根版本并运行 `pnpm run release:verify --family dsh`。manifest 中的版本表示准备状态；只有已发布 release 及其固定标签才能标识已交付字节。检查 release notes 中的分发范围、确切提交、CI 来源与未完成验收。不要仅凭可变分支或本地标签推断最新发行版本。

首个 1.0 候选版的标签是 `harniverse-v1.0.0-rc.1`，稳定化分支是 `release/1.0`。在该版本线上工作时，从远端解析标签和分支。发布后分支可以继续前进，标签保持固定。本文件是策略，不是持续追加的发布账本。

## 版本身份

workspace 根与 dsh 产品族共用一个版本。vendored 框架包与 native 包保留独立版本线。包 scope、插件身份、产品版本、Git revision 和持久数据版本彼此独立；产品发布不会重命名继承的包命名空间，也不会重新发布无关的包族。

候选版使用 `major.minor.patch-rc.N`，稳定版使用 `major.minor.patch`。准备一个真正用于发布的新候选版时才递增 `N`，不要为每个提交、修复或 PR 递增。即使 manifest 保留候选版本号，尚未发布的集成提交也由 Git SHA 区分。只有提交与标签提交相同的 checkout 才能被描述为确切的已发布候选版。

RC 递进与稳定版晋升使用显式版本：`1.0.0-rc.1` → `1.0.0-rc.2` → `1.0.0`。当前 bump 命令在 `1.0.0-rc.1` 后执行 `patch` 会得到 `1.0.1`，并不表示“去掉 RC 后缀”。该命令不接受 `+sha` 等 build metadata。对于已声明支持的 API，兼容修复使用 patch，兼容新增使用 minor，破坏性变更使用 major。

产品版本编号不会覆盖持久格式承诺。Session 格式 `v0` 永久只允许追加，即使产品跨 major 版本也不例外。SQLite schema 版本独立且单调递增；不能仅凭产品版本推断数据库支持降级。首个稳定版之前必须复核根目录说明中的预发布立场；RC 不会使该立场失效。

## 分支职责与准入

| Ref | 职责 | 准入规则 |
|---|---|---|
| `dev` 与功能分支 | 准备、评审集成工作 | 保持插件原生架构，不影响无关工作。 |
| `master` | 集成开发，包括面向后续版本的工作 | 现有受支持行为与契约保持有效；未完成功能满足下述隔离规则。 |
| `release/1.0` | 稳定化 1.0 版本线 | 仅选择该版本需要且完整、经过评审的改动；不自动吸收后续功能开发。 |
| `harniverse-v<version>` | 确切的已发布源码身份 | 在已验证发布提交上创建附注标签；不得移动或复用已发布标签。 |

未完成功能只有在默认关闭或不注册到已交付 profile/composition、不暴露未完成的公开路由、命令或契约，并且不破坏现有行为、测试或持久格式时，才能进入集成分支。只隐藏按钮不足以形成隔离。通过插件配置与组合实现隔离，不要在 agent loop 中增加提供商或功能特例。无法隔离的改动保留在功能分支，直到满足准入要求。

在选定的首个候选提交上建立稳定化分支。此后明确选择进入该版本线的修复，不要整体合并 `master`。移植已评审改动及必要依赖，针对稳定化源码解决冲突，并验证最终代码树。先在稳定化分支完成的修复也要带回集成分支，避免后续开发重新引入缺陷。具体 Git 操作遵守已授权工作流；本策略本身不授权提交、切换分支、推送、合并或发布。

RC 编号不是功能开发里程碑。即使部分实现已进入 `master`，未完成功能仍须排除在候选版之外，直到完成。稳定版发布还要求该版本声明的验收全部完成；不能通过重新贴标签绕过性能、签名或分发要求。

## 准备并发布候选版

1. 明确已授权的发布范围和确切目标分支。检查工作区与远端 refs，保留无关改动。选择尚未使用的新版本，并确认目标标签和 registry 版本没有代表另一组字节。当前 bump 工具没有强制执行所有版本单调性或标签复用规则，操作者必须完成这些检查。
2. 使用 `pnpm run release:dsh --dry-run 1.0.0-rc.2` 预览，再用 `pnpm run release:dsh --no-commit 1.0.0-rc.2` 准备。将示例版本替换为选定版本，晋升稳定版时显式使用 `1.0.0`。评审全部产品族 manifest 和 lockfile。准备命令不会暂存或提交；lockfile 同步失败时保留已写 manifest 供检查。
3. 通过已授权 Git 工作流评审并集成准备好的版本。按改动运行针对性的本地检查；完整检查由 CI 按根目录说明执行。核验确切选定提交的 CI 与打包，或记录相同的受测代码树及独立验证的打包提交。推送发布分支本身不证明所有现有 workflow 都会在该分支运行；发布前检查触发条件并安排必要 PR 或手动验证。
4. 在已验证提交上创建并推送附注标签 `harniverse-v<version>`。首个候选版还须在同一提交建立稳定化分支。确认远端分支与剥离后的标签目标。不得为了纳入修复而重新指向已发布候选标签；应发布下一个候选版。
5. 编写 release notes，列出版本、提交、分支、受支持安装路径、附件范围、CI 证据与剩余限制。如果已授权的分发范围是源码和开发者制品，附上经过验证的制品、来源信息和校验值。RC 标记为 prerelease，不标为稳定 latest。GitHub 发布不表示已完成 npm、PyPI 或已签名桌面版发布。
6. Registry 发布是独立的显式操作，使用匹配标签与受保护 workflow。npm 预发布版本使用 `next`，稳定版本使用 `latest`；必须确认目标分发所需的 scope 所有权与凭据。桌面分发要求独立的签名、公证和最终产物验证。不能仅因 manifest 中存在继承的命名空间，就向该命名空间发布。
7. 回读已发布 release，下载附件并核对哈希是否与目标字节一致。检查远端标签身份和最终仓库状态。将版本特定证据记录在该 release 的说明与元数据中，不建立新的中央账本。明确保留尚未完成的验收事项。

## 失败或被替代的发行版本

发布前，尚在验证制品的草稿可以修正。发布后，源码标签与带版本制品保持固定。Registry 上传失败只能使用同一组已验证字节重试；完整性不匹配时必须使用新版本。附件缺失或撤下不意味着可以静默替换已发布内容。在 release notes 中说明撤回或已知缺陷，并以新版本发布修正后的候选版。

这些规则将集成速度与发布稳定性分开：未完成功能可以通过插件边界推进，同时不静默改变现有候选版。验证证据、发布范围与确切源码身份始终能从仓库及发布制品中恢复。
